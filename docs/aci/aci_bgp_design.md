# ACI BGP Design

Regardless if the Basic Design or the Advanced Design is used, the ACI BGP configuration remains largely identical.

The goal of the ACI fabric in this context is to provide reliable transport and security for the Kubernetes infrastructure. As covered in the [ACI Designs](../aci_designs) section, ACI requires configuration with a Bridge Domain and L3Out to establish connectivity to the clusters.

## L3Out Physical Connectivity

There is no strict requirement for the physical connectivity of the L3Out, provided it meets the necessary redundancy level. Implementing L2 redundancy can improve failover times by eliminating the need to wait for BGP convergence.

This design utilizes the floating SVI feature for L3 connectivity. This feature enables the configuration of an L3Out without specifying logical interfaces, thereby removing the need to configure multiple L3Out logical interfaces to maintain routing when VMs migrate between hosts. Floating SVI is supported for VMware vSphere Distributed Switch (VDS) starting from Cisco ACI Release 4.2(1) and on physical domains starting from Cisco ACI Release 5.0(1). Using physical domains is recommended for the following reasons:

* Support for any hypervisor.
* Support for mixed-mode clusters (VMs and bare-metal).

This recommendation is not a strict requirement. If all nodes operate within a VMware environment, there are no technical impediments to using VMM integration.
Employing floating SVI also relaxes the constraint against Layer-2 communications between the `nodes`, enabling the design to utilize:

* A single subnet for all `nodes`.
* A single encapsulation (VLAN) for all `nodes`.

### BGP Dynamic Neighbors

All `nodes` configured for BGP peering will share the same AS number. Sharing the same AS number allows the design to leverage the BGP Dynamic Neighbors capability. This feature facilitates the dynamic and automated establishment of peering sessions between routers. Instead of mandating manual configuration of individual neighbor statements for each peer, this feature employs a `listener` (the ACI fabric in this context) to accept incoming BGP connections from a predefined IP subnet.

### BGP Peering with ACI Prior to 6.1(2)

In ACI software releases before 6.1(2), a specific peering configuration is necessary: `ingress nodes` must be peered *either* exclusively with directly attached anchor nodes *or* exclusively with non-directly attached anchor nodes.

This requirement exists because routes generated by nodes directly connected to anchor nodes are preferred over routes from nodes not directly connected. This preference can lead to certain nodes being underutilized or not utilized at all.

For example, if a service with the IP address `1.1.1.1` is exposed via BGP, an anchor leaf like `leaf101` will only install one ECMP path for `1.1.1.1/32` through `192.168.2.1` if that path originates from a directly connected node. The locally attached route is preferred, even if multiple nodes could potentially provide the service.

This limitation was removed in ACI release 6.1(2). Therefore, using ACI 6.1(2) or a newer version is strongly recommended.

### Next-Hop Propagation and Ignore IGP Metric - ACI 6.1(2)+ Required

{: .warning }
These two features are recommended for the *Basic Design* and are a **requirement** for the *Advanced Design*.

When an external router is physically connected to a non-anchor leaf node, traffic originating from a Cisco ACI internal endpoint destined for an external location typically routes through an anchor leaf node before reaching the external router via the non-anchor leaf. This results in a suboptimal traffic path. Furthermore, as previously noted, the preference for routes from nodes directly connected to anchor leaves can lead to the underutilization of nodes not directly connected.

Enabling the following two features addresses both of these issues:

* **Next-Hop Propagation:** This configuration is applied exclusively to the anchor leaf nodes. It allows them to redistribute external prefixes within the Cisco ACI fabric, using the next-hop IP address of the external router that announced these prefixes. Consequently, compute leaf nodes receive and install these external prefixes in their forwarding tables with the external router's IP address (the Cilium Ingress Gateway in this design) as the next-hop.

* **Ignore IGP Metric:** Configuring this option modifies the BGP best path algorithm to disregard the IGP metric associated with the next hop. This change allows nodes connected to both anchor and non-anchor leaves to be selected as valid next hops, ensuring that all Kubernetes (`K8s`) nodes are effectively utilized.

It is important to note that the Next-Hop Propagation feature was introduced in ACI release 5.0(1). However, support for the Ignore IGP Metric feature was not available until ACI 6.1(2). For this design to function optimally, both features are required. Configuring only Next-Hop Propagation is insufficient. If the environment runs ACI 6.1(1) or an earlier version, the recommendation is to connect the `ingress nodes` directly to the `ACI Anchor nodes`.

### Max BGP ECMP Path (Optional)

By default, ACI installs a maximum of 16 eBGP/iBGP Equal-Cost Multi-Path (ECMP) paths. If the deployment requires more than 16 `nodes`, ACI can be configured to support up to 64 ECMP paths.

### BGP Graceful Restart

Both ACI and Cilium should be configured to utilize BGP Graceful Restart. This feature ensures that when a BGP speaker restarts its BGP process or if the process unexpectedly terminates, its neighbors retain the previously received paths. This mechanism maintains connectivity without disruption, provided the data plane remains correctly programmed during the restart.

### BFD with Cilium BGP

Bidirectional Forwarding Detection (BFD) is a network protocol designed to detect faults along the path between two forwarding engines, like routers. It is frequently used alongside routing protocols such as BGP (Border Gateway Protocol). BFD complements BGP operations by offering rapid and dependable detection of link failures, which facilitates faster failover and enhances overall network resilience. Leveraging this capability makes it possible to achieve sub-second failure detection for the BGP peering sessions.

{: .warning }
If BFD is configured for sub-second failure detection and virtual machines are in use, a live migration event might cause BFD to incorrectly perceive the migrating node as down. This can trigger a BGP session reset, resulting in the withdrawal of all routes previously advertised by that node from the routing table.

### BGP Hardening (Optional)

To safeguard the ACI system against potential BGP misconfigurations originating from the Kubernetes environment, implementing the following hardening measures is recommended:

* Enable BGP password authentication between peers.
* Set the maximum accepted AS-path length limit to one.
    * Based on the eBGP design described, the expected AS path length should consistently be one.
* Configure BGP import route control policies to accept only the anticipated external service subnets.
* (Optional) Impose a limit on the maximum number of prefixes accepted from the `nodes`.
